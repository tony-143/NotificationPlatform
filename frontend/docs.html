Getting started

The API is a JSON/HTTPS service. Requests are authenticated with an API key created in API Keys. Each account has exactly one active key at a time.

Base URL
http://localhost:8081
Content type
application/json
Auth header
X-API-Key
Idempotency header
Idempotency-Key (required on create)

Three public operations are available: create a notification, read one notification, and list your notification history. They are also served under the /api/v1/notifications alias.

Notifications are processed asynchronously. A 202 Accepted response means the notification was stored — not that it was delivered.

Authentication

Send the secret from your API key in the X-API-Key header. This backend does not use Authorization: Bearer for notification calls — a Bearer token is silently ignored and the request fails with 401.

HTTP headers
Content-Type: application/json
X-API-Key: np_YOUR_API_KEY
Idempotency-Key: order-1042-email

Keys are bound to the account that created them. Requests cannot select another tenant: the server derives ownership from the key itself.

Use API keys only from a trusted server. Never embed them in browser JavaScript, mobile apps, public repositories or client-side logs.

A missing, malformed, expired or revoked key returns 401 Unauthorized with the body {"message":"A valid API key is required"} or {"message":"Invalid or revoked API key"}.

Create a notification

POST /api/notifications alias: /api/v1/notifications

Stores a notification for asynchronous processing. Returns 202 Accepted for a new request, or 200 OK with duplicate: true when the same Idempotency-Key and payload were replayed.

Request headers

HeaderRequiredNotes
Content-TypeYesapplication/json
X-API-KeyYesActive key for your account
Idempotency-KeyYes1–200 characters; unique per logical request for 5 minutes

Request body

FieldTypeNotes
typestringEMAIL or SMS (case-insensitive)
recipientstringEmail address or phone number, max 512 chars
messagestringRequired, max 10,000 chars
payloadstringOptional JSON-encoded string, max 100,000 chars
scheduledAtISO-8601 instantOptional; must not be in the past

payload is a string, not a nested object. Serialize your JSON first: "payload": "{\"orderId\":1042}".

JavaScript (server-side)

Node.js 18+
const response = await fetch(`${process.env.NOTIFICATION_API_URL}/api/notifications`, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-API-Key': process.env.NOTIFICATION_API_KEY,
    'Idempotency-Key': crypto.randomUUID()
  },
  body: JSON.stringify({
    type: 'EMAIL',
    recipient: 'customer@example.com',
    message: 'Your order #1042 has shipped.',
    payload: JSON.stringify({ orderId: 1042 })
  })
});

const result = await response.json();
if (!response.ok) {
  throw new Error(result.message || `Request failed: ${response.status}`);
}
console.log(result.notification.id, result.duplicate);

Idempotency

                    

                        Every create request must include Idempotency-Key. The server
                        hashes the key and the validated request body, and remembers the pair for
                        5 minutes.
                    

                    
    
                        
  • New key → 202 Accepted, notification stored, duplicate: false.
    • 
                        
  • Same key + same body within 5 minutes → 200 OK, the original notification is returned, duplicate: true. No second notification is created.
    • 
                        
  • Same key + a different body → 409 Conflict with "Idempotency-Key was already used with a different request".
    • 
                        
  • After 5 minutes the record expires, so the same key can be used again.
    • 
                    

                    

                        Reuse the same value when retrying the same logical notification (for example after a
                        timeout). Generate a new value for every different notification. A UUID or a deterministic
                        business key such as order-1042-email both work.
                    

                


                

                    
Scheduling

                    

                        Set scheduledAt to an ISO-8601 instant to delay processing.
                        The scheduler only picks up notifications whose scheduled time has passed.
                    

                    

                        
cURL

                        
curl -X POST "http://localhost:8081/api/notifications" \
  -H "Content-Type: application/json" \
  -H "X-API-Key: np_YOUR_API_KEY" \
  -H "Idempotency-Key: reminder-2026-11-01" \
  -d '{
    "type": "EMAIL",
    "recipient": "customer@example.com",
    "message": "Your subscription renews tomorrow.",
    "scheduledAt": "2026-11-01T09:00:00Z"
  }'

                    

                    

                        A time in the past returns 400 Bad Request (a 60-second grace
                        period is allowed). Scheduled notifications stay PENDING until
                        they are due. Align this with server time (UTC in the examples).

cURL

                        404 Not Found, not 403, so ids cannot
                        be enumerated across tenants.
                    


                    
Status values

                    

                        
StatusMeaning

                        
                            
PENDINGQueued or waiting for its scheduled time.

                            
PROCESSINGA worker has claimed it and is attempting delivery.

                            
RETRYINGA transient failure occurred; another attempt is queued.

                            
SENTThe provider accepted the message. Not a delivery receipt.

                            
FAILEDDelivery failed permanently or retries were exhausted.

                            
CLOSEDThe notification was closed without a send.

                            
PROVIDER_NOT_CONFIGUREDNo email provider is configured on the server; nothing was sent.

                        
                    

                    

                        There is no DELIVERED status. This backend does not ingest
                        delivery receipts from providers, so the portal never claims confirmed delivery.
                    

                


                

                    
List notification history

                    

                        GET
                        /api/notifications
                    

                    

                        Returns all notifications for the key's account, newest first. The public API returns a
                        plain array and is not paginated.
                    

                    

                        
JavaScript

                        
const response = await fetch(`${process.env.NOTIFICATION_API_URL}/api/notifications`, {
  headers: { 'X-API-Key': process.env.NOTIFICATION_API_KEY }
});

if (!response.ok) {
  throw new Error(`History request failed: ${response.status}`);
}

const notifications = await response.json();
for (const item of notifications) {
  console.log(item.id, item.type, item.status, item.createdAt);
}

                    

                    

                        For paginated, filterable history use the dashboard endpoints below. They are
                        session-authenticated and scoped from the signed-in account, so they are not usable with
                        X-API-Key.

Errors use a consistent JSON body:

  "timestamp": "2026-10-27T16:45:03.305948700Z",

  "error": "Bad Request",
  "message": "Notification type must be EMAIL or SMS",

Rate limits & quotas

                    

                        This backend does not implement request rate limiting, quotas or per-key throttles, and it
                        does not track API request counts. No 429 responses are produced
                        and no X-RateLimit-* headers are returned.
                    

                    

                        Because usage analytics are unavailable, the Dashboard reports notification outcomes only.
                        If you need request-level metrics, they must be added at the gateway or in a dedicated
                        audit table — the portal intentionally does not fabricate them.
                    

                


                

                    
Email & SMS support

                    

                        EMAIL is delivered through the configured SMTP server. If SMTP
                        credentials are absent, the notification is stored and then marked
                        PROVIDER_NOT_CONFIGURED; the create call still returns
                        202.
                    

                    

                        SMS is accepted and stored but no SMS gateway is integrated in
                        this repository. SMS notifications therefore end in
                        PROVIDER_NOT_CONFIGURED as well. Treat the SMS channel as a
                        schema-level placeholder until a gateway is added.
                    

                    

                        Recipients are validated for length only. The backend does not verify that an email address
                        or phone number exists.
                    

                


                

                    
API key security

                    
    
                        
  • The server generates 32 random bytes from SecureRandom, URL-safe Base64 encodes them and prefixes np_.
    • 
                        
  • Only a SHA-256 hash and an 11-character prefix are stored. The raw secret is shown once and cannot be recovered.
    • 
                        
  • Rotating a key replaces the hash in place — the previous secret stops working immediately.
    • 
                        
  • Revoking a key sets its status to REVOKED; the row is retained for audit, and authentication then returns 401.
    • 
                        
  • Ownership is always resolved from the authenticated principal, never from a tenant id supplied by the caller.
    • 
                    

                    

                        Recommended: keep the key in environment variables or a secrets manager, use a separate
                        account/key per environment where possible, and rotate immediately if a key is exposed.

Troubleshooting

                    
401 on every request

                    
    
                        
  • Header name must be X-API-Key, not Authorization.
    • 
                        
  • The key may have been rotated or revoked — fetch the current prefix on the API Keys page.
    • 
                        
  • Copy the whole secret including the np_ prefix; whitespace breaks the hash.
    • 
                    

                    
409 Idempotency conflict

                    

                        The same Idempotency-Key was used with a different body within
                        5 minutes. Use a fresh key for a genuinely different notification.
                    

                    
Notification stays PENDING

                    

                        Check scheduledAt (future values wait) and the server scheduler
                        logs. A pending row is not an error.
                    

                    
PROVIDER_NOT_CONFIGURED

                    

                        SMTP credentials are missing or the SMS gateway is not integrated. Add SMTP settings to
                        local-secrets.properties and restart the backend, then send a new
                        notification.
                    

                    
Dashboard is empty

                    

                        Metrics are scoped to the signed-in account. If you sent notifications with a different
                        account's key, they will not appear here. Start with
